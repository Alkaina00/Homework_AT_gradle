## Оценка в целом

Проект — набор учебных домашних заданий на Java 17 + Gradle. Архитектура
**адекватна цели**: каждая домашка лежит в своём пакете, тесты отделены от
продакшен-кода, стек согласован (JUnit 5, RestAssured, Cucumber, Hamcrest).
Это хороший «песочный» монорепозиторий для отработки Java.

Важные плюсы:
- Чёткое разделение `src/main/java` и `src/test/java`.
- Пакеты сгруппированы по домашним заданиям (homework11…homework18) — легко
  находить и поддерживать.
- Единый `build.gradle` с версиями зависимостей в одном месте.
- REST-набор homework17/18 логически упорядочен через `@TestMethodOrder`
  + `@Order`, что повторяет реальный CRUD-сценарий.

## «Жёлтые зоны» (стоит исправить)

1. **Захардкожен `baseURI` в каждом тесте.**
   В `ServeRestTest` и `ServRestHW18Test` адрес задан в `@BeforeAll`.
   Если стенд сменится — придётся править оба файла.

2. **Дублирование RestAssured-настроек (baseURI, логирование).**
   Один и тот же блок в двух тестовых классах. Дубли у вас уже устраняются
   вручную (см. п.2 в разделе «зелёное»).

3. **Данные в тестах захардкожены** (email `fulano@qa.com` / пароль `teste`,
   `secret123`). Для учебной задачи допустимо, но в боевом проекте —
   файлы конфигурации / переменные окружения.

4. **Хрупкие порядковые связи между тестами.**
   В `ServRestHw18Test` `shouldUpdateProductPrice` / `shouldDeleteProduct`
   используют результат `shouldCreateProduct` через `productId`. Если тест
   запустить отдельно — упадёт. Для учебного класса приемлемо, альтернатива —
   `@BeforeEach`-подготовка или изоляция данных.

5. **Cucumber: шаги только печатают в консоль**, а не делают реальных
   вызовов и проверок (homework16). Для домашней задачи — ок, но это
   «заготовка», а не проверяющий тест.

## «Маленькие замечания» (косметика)

- `ServRestHW18Test` и `ServRestTest` схожи по структуре; стоит один
  общий базовый класс или `RestAssured`-конфиг в одном месте.
- В `BookingSteps` много `System.out.println`, дублирующих логику; при росте
  набора лучше выносить состояние ресторана в реальные объекты-фикстуры.

## «Зелёное» (что уже хорошо)

- Юнит-тест `XMLUtilsTest` изолирован и не зависит от сети.
- `@Order` + `@TestMethodOrder` дают читаемые CRUD-цепочки.
- Файлы `.feature` читаемые, с тегами (`@smoke`, `@negative`, `@regression`,
  `@review`).
- Стандартная папка `src/test/resources/features` — корректное место для
  фича-файлов.
- Одна репо: легко нажать «запустить всё» и видеть итог по заданиям.
